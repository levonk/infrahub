# Private NPM Registry Recommendation

Date: 2026-08-04

## Executive Summary

After comprehensive research and comparison of five candidate solutions (Verdaccio, Sonatype Nexus, cnpmcore, pnpr, and Artifactory OSS), **Verdaccio is the clear recommendation** for this use case.

## Requirements

1. Proxy and cache npmjs.org packages locally (faster installs, offline resilience)
2. Allow publishing private packages (scoped, e.g., @levonk/*)
3. Deploy as Docker container on:
   - Oracle Cloud ARM64 server (cno) — small instance
   - Windows Docker Desktop X86 machine (nl)
4. Fronted by Traefik with Authelia SSO for web UI
5. htpasswd/bcrypt auth for npm CLI publish operations
6. Support LRU storage eviction (auto-cleanup when storage fills)

## Recommendation: Verdaccio

### Why Verdaccio fits

- **Resource footprint**: 512MB-1GB RAM (vs 6-8GB+ for Nexus/Artifactory). Fits the small OCI ARM64 instance.
- **Multi-arch Docker**: Official amd64 + arm64 images (~67MB compressed). Works on both targets without custom builds.
- **Zero database**: Tiny JSON database built-in. No PostgreSQL/MySQL/Redis to provision.
- **Auth model**: Built-in htpasswd/bcrypt — exactly what npm CLI needs for `npm login` / `npm publish`.
- **Traefik compatibility**: Documented X-Forwarded-* header support, `VERDACCIO_PUBLIC_URL` env var for reverse proxy.
- **Config complexity**: Single YAML file. Ansible can render it from Jinja2 templates.
- **Active development**: 17.8K GitHub stars, releases every 1-10 days, MIT licensed, 8+ years old.

### The only gap: Storage eviction

Verdaccio lacks automatic LRU storage eviction. Options:
1. **Cron job**: `find /verdaccio/storage -type f -mtime +90 -delete` (simple, sufficient for personal use)
2. **Storage plugin**: Custom plugin for LRU eviction
3. **Manual cleanup**: For personal use with scoped packages, storage growth is manageable

For this use case (personal scoped packages + npmjs.org proxy cache), storage eviction is a minor concern. The proxy cache can be wiped entirely without data loss — only published @levonk/* packages need persistence.

## Why not the alternatives?

- **Sonatype Nexus**: 8GB+ RAM, requires PostgreSQL, overkill for npm-only. Only worth it if multi-format support (Maven, Docker, PyPI) is needed.
- **cnpmcore**: No multi-arch Docker (ARM64 unsupported), requires MySQL + Redis + S3. Overkill.
- **pnpr**: Experimental, no official Docker images, no multi-arch. Not production-ready.
- **Artifactory OSS**: 6GB+ RAM, requires PostgreSQL, SAML/OAuth not in OSS. Overkill.

## Deployment architecture (for this project)

Two independent Verdaccio instances with synced config (same htpasswd, same config template rendered by Ansible):

- **cno (oci-cloud-server, ARM64, Linux)**: `community.docker.docker_container` module, joins `traefik-network`, Traefik routes `npmjs.cno.levonk.com` to it.
- **nl (dtop202311, X86, Windows Docker Desktop)**: `ansible.builtin.shell` + `DOCKER_HOST: ssh://` + `delegate_to: localhost` (QM pattern — community.docker modules fail on Windows). Traefik on OCI routes `npmjs.nl.levonk.com` to the Windows host's Tailscale FQDN + host port.

Both use the upstream `verdaccio/verdaccio:latest` image (no custom build needed). Ansible renders `config.yaml` from Jinja2 templates. htpasswd generated by Ansible from vault secrets.

## Image strategy decision

**Upstream image + Ansible Jinja2 templates** (not the existing custom Dockerfile):

- The existing scaffolding's custom entrypoint uses `sed` for env-var substitution — fragile with special characters in passwords. Ansible Jinja2 is more robust and is the project standard.
- The custom Dockerfile is `FROM verdaccio/verdaccio:latest` — using the upstream image directly gives the same verdaccio version without a build pipeline.
- Eliminates Phase 3 (build pipeline, multi-arch buildx, registry push) entirely.
- Aligns with the current Ansible-managed service standard (ai-litellm, ai-qm, proxy-traefik all use Jinja2 templates).
- The custom image adds curl/gettext/yamllint/bash/su-exec — with Ansible managing config, these aren't needed at runtime. Healthcheck uses Ansible's `wait_for` instead of in-container curl.
